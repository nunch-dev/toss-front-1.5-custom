# 네이티브 WSS 시험 기록

## 환경과 재현

- Swift 6·CryptoKit·URLSession 요청기와 Bun 1.4.2 중계 서버를 같은 Mac의 loopback에서 시험했다.
- `bun run test:macos`가 임시 인증서와 키를 생성하고 종료 시 해당 디렉터리를 제거한다.
- 실제 시스템 신뢰 저장소·로그인 권한·키체인은 변경하지 않았다.

## 가설과 관찰

1. 인증서 조건 불충족: macOS 기록에서 `Trust evaluate failure: [leaf ServerAuthEKU]`를 확인했다.
2. 요청 수명이나 제어 파이프의 취소: 실패가 30초 제한보다 훨씬 빨랐고 종료 코드는 파이프 취소의 2가 아니었다.
3. HTTP/WebSocket 단계의 거부: 관찰된 실패는 TLS 신뢰 평가 단계였다.

시험 인증서의 서버 인증 용도 조건 불충족이 확인됐다. 사용자에게 프로파일 수정·재발급 범위를 설명했고 2026-11-20 “진행해.” 승인을 받은 뒤, 임시 CA와 서버 인증서를 분리했다. 서버 인증서에는 CA:FALSE, serverAuth, 서버 호스트명을 명시했다. TLS 검증 조건과 시스템 신뢰 저장소는 변경하지 않았다.

재시험에서 정상 승인·거부와 신뢰하지 않는 CA·잘못된 호스트명 거부는 통과했다. 파이프 취소는 종료 133으로 실패했다. 시험 프로세스의 크래시 보고서에서 `_dispatch_assert_queue_fail` → `_swift_task_checkIsolatedSwift` → `closure #1 in static RequestorConformanceMain.main()`을 확인했다. MainActor 문맥을 상속한 콜백이 전역 Dispatch 큐에서 실행된 것이 원인이며, 캡처 없는 콜백을 `@Sendable`로 명시해 격리 문맥 상속을 제거했다. 오류를 숨기는 대신 기존 종료 2·결과 없음·서버 취소 통지 검증을 유지하고 stderr가 비어 있는지도 확인한다.

## 임시 진단과 정리

- NSError의 domain·code 출력만 임시 추가해 NSURLErrorDomain -999를 확인했으며 해당 진단 출력은 제거했다.
- 로그 조회는 시험 요청기 프로세스의 인증서·신뢰·취소 기록으로 제한했다.
- 임시 TLS 디렉터리는 시험 스크립트의 종료 처리로 제거됐다. 실행 중인 시험 서버·클라이언트는 없다.

## 검증 상태

최종적으로 Swift와 jose의 서명·검증 상호 운용 및 입력 검증 22개, 네이티브 WSS 승인·거부·취소와 미신뢰 CA·잘못된 호스트명 거부 5개가 모두 통과했다. 총 27개 시험·45개 assertion·실패 0개다. Swift 6 경고 오류 처리 빌드, 타입·린트·포맷 검사도 통과했다.

기존 인증서 검증 조건을 우회하거나 실패 시험을 약화하지 않았다. 동일 CA의 정상 호스트명과 잘못된 호스트명 인증서를 사용해 정상 연결과 호스트명 거부를 구분했다. 실제 Mac 잠금 해제나 설치용 인증 플러그인 검증은 이번 결과에 포함하지 않는다.

## 2026-11-23 진단 호출기의 권한 조회 오류

재현 명령은 프로젝트의 `private/macos-auth-probe-20261120/run-probe --screen-trial`이다. 화면 잠금 규칙을 연결하기 전, 항상 거부하는 별도 시험 권한의 로그 수집을 확인하다 실패했다. 실제 화면 잠금은 시도하지 않았다.

- 호출기: `PROBE_PROCESS pid=12924 uid=501`
- 실패: `PROBE_RIGHT_LOOKUP_FAILED status=-60008`, 종료 1
- 같은 시험 권한의 `/usr/bin/security authorizationdb read` 결과: 종료 0, `YES (0)`
- 코드 서명: `flags=0x20002(adhoc,linker-signed)`, `Signature=adhoc`
- `codesign --verify --strict` 결과: 종료 0, `valid on disk`, `satisfies its Designated Requirement`
- 09:45:21.886 authd 기록: `process: PID 12924 failed to create code ref 100001`
- 같은 시각의 authd 기록: `xpc: failed to register connection (PID 12924)`

가설은 호출기 서명 문제, Desktop 경로에 대한 authd 접근 제한, 시험 권한 등록 또는 서비스 문제로 나눴다. 등록된 권한은 읽히고 디스크 서명 검증은 통과했다. 같은 시각 커널에서 `sandboxd rejected approval request from authd for kTCCServiceSystemPolicyDesktopFolder`와 `would require prompt`, 해당 호출기 경로의 `deny(1) file-read-data`를 확인했다. authd가 Desktop 아래 호출기를 읽지 못해 코드 참조 생성과 연결 등록이 실패했다.

이 접근 차단을 받은 실행은 재시도하지 않는다. 보호 설정을 변경하지 않고 호출기 한 파일을 기존 Shared 시험 폴더에 배치하는 별도 실행은 사용자에게 범위를 설명하고 새 확인을 받은 뒤에만 진행한다. 경로를 바꾼 실행 결과는 아직 검증하지 않았다.

이번 시험 자료는 `private/macos-screen-trial/manual-20261123.Pg6HBN/`에 보존한다. `control-caller.log`는 stdout만 담고, 위 실패 stderr는 호출 감시 결과에서 확인했다. 별도 디버거·계측 코드·개인키 파일은 만들지 않았다.

사용자가 호출기 한 파일의 Shared 배치·실행을 승인했다. 같은 파일을 `/Users/Shared/plf-screen-trial.Vn1a5f/run-probe`로 복사했고 `cmp -s`가 종료 0이었다. 서명·보호 설정·코드는 바꾸지 않았다. 새 실행은 `PROBE_PROCESS pid=27501 uid=501`, `PROBE_RIGHT_RESULT status=-60005 release=0`, 종료 0이었다. 09:54:06.759의 SecurityAgentHelper-arm64 PID 27607 로그에서 설치된 진단 번들의 `AUTH_PROBE_CONTEXT`와 `AUTH_PROBE_INVOKED result=deny`를 확인했다.

관찰된 호출자 상태는 `caller_session=101395 session_status=0 attributes=0 evaluation_status=0 evaluation_present=0 console_uid=501 cg_uid=-1 on_console=0 login_done=0`이다. UID 일치와 별도 권한의 거부 성공을 실제 잠금 대상 세션 결합으로 해석하지 않는다. Desktop 실행 실패와 승인된 Shared 실행 성공을 같은 바이너리로 구분했으며, 차단된 Desktop 실행을 반복하거나 TCC 보호를 완화하지 않았다.

## 로컬 계약 v2의 검증용 변이 계획

실제 화면 호스트 UID 92와 대상 콘솔 UID 501을 분리한 로컬 정책·파이프 v2를 구현한다. 네이티브 공유 context 39개, 응답 경계 62개, owner 콜백·취소·변경 감지 82개 검사가 정상 소스에서 통과했다. 이는 실제 서명 화면 승인이나 키체인 사용 가능성의 증거가 아니다.

검증용으로만 `private/macos-approval-20261120/mutation-v2.*`에 소스 세 파일의 복사본과 시험 실행 파일을 만들 예정이다. 운영 소스는 변이하지 않는다. 공유 context의 root/remote 차단, 응답 context 숫자 필드 결합, owner의 최종 context 확인을 각각 깨뜨려 해당 시험의 실패를 확인한다. 모든 변이 디렉터리는 결과를 기록한 뒤 제거하며 설치물에 포함하지 않는다.

세 변이는 각각 `FAIL root session rejected`, `FAIL changed context field rejected in either frame`, `FAIL screen context missing-after result`에서 종료 1로 실패했다. 컴파일 오류가 아닌 해당 동작 검사의 실패였다. 사용한 `mutation-v2.Iul9WQ` 디렉터리는 종료 0으로 제거했다. 운영 소스는 바꾸지 않았으므로 이미 통과한 검사를 반복 실행하지 않았다.

변경된 호출 형식으로 실제 자식 프로세스를 생성하는 Runner 시험도 55개 검사를 통과했다. 통합 번들 빌드는 종료 0이고 실제 helper CDHash는 `1986ebc7d7ec01f3c3f0ff07bf5092152d2dc649`다. 고정 해시·hardened runtime·entitlement 부재 검증과 다른 실행 파일의 대체 거부를 확인했다. 새 v2 번들은 아직 시스템에 설치하지 않았다.

## 2026-11-23 설치 쉘의 조건식 종료 결함

v2 설치 준비 중 일반 사용자 UID 501로 설치·정리 스크립트의 조기 거부를 검사했다. 종료 코드는 예상한 1이었지만 stderr에 `restore: No such file or directory`가 나타났다. 종료 코드만으로는 비관리자 차단을 증명할 수 없었다. `bash -x`에서 `[[ 501 -eq 0 ]]` 실패 후 `codesign --verify`까지 진행한 것을 확인했다. 그 서명 검사에서 종료했으므로 설치 단계에는 도달하지 않았다.

현재 `/bin/bash`는 3.2.57이다. 같은 실행 환경에서 `set -e; [[ 1 -eq 0 ]]; printf 'CONDITIONAL_CONTINUED\n'`는 끝까지 진행했고, `set -e; false; printf 'SIMPLE_CONTINUED\n'`는 false에서 종료했다. BASH_ENV의 보호 설정을 제거하거나 변경하지 않았다. 초기에는 실행 도구의 차이도 의심했지만 실제 터미널에서도 같은 조건식 문제가 재현됐다.

`macos/screen-trial/tests/InstallGuards.sh`는 실제 스크립트를 비관리자로 실행하고 기대 종료 코드와 빈 출력을 함께 검사한다. 수정 전 `INSTALL_GUARD_FAIL expected=1 actual=1 output=.../restore: No such file or directory`로 실패했다. 설치·정리 스크립트의 인수·UID·정책·파일 조건식에 명시적인 `|| exit 1`을 붙여 Bash의 암묵적 종료에 의존하지 않도록 수정했다. 이 검사는 관리자 설치 성공이나 실제 화면 해제를 검증하는 시험이 아니다.
