# 별도 인증 권한 설치 시험 준비

## 현재 상태

2026-11-20 현재 소스·로컬 빌드·서명 및 구성요소 시험에 이어, 실제 인증 호스트에서 전용 권한의 조건부 승인·거부·만료·연결 취소 시험을 완료했다. 시험 권한·번들·전용 키·공유 임시 폴더는 모두 제거했다. 기본 빌드 산출물은 정책과 전용 키가 없는 상태이며 그대로 설치할 수 없다.

첫 시도에서는 사용자 승인 후 전용 정책·키·로컬 중계와 Shared 시험물을 준비했지만 관리자 실행이 180초 뒤 시간 초과됐고, 인증창 상태 질문도 30분 동안 응답이 없었다. 2026-11-20 15:56의 확인에서 새 번들·키 디렉터리·시험 권한은 없었으며 기존 screensaver 규칙과 미설정 screenUnlockMode는 그대로였다.

첫 시도의 서버·로그 수집·공유 시험물과 비밀키 복사본 6개를 정리했다. 이후 사용자가 인증창 재표시를 요청해 새 키와 정책을 준비했으며, 관리자 설치와 아래 실제 호스트 시험을 수행한 뒤 정리까지 완료했다.

## 실제 인증 호스트 시험 결과

호스트는 `SecurityAgentHelper-arm64`, UID 501이다. 실제 플러그인 경로에서 `PLF_APPROVAL_INVOKED`와 결과 이벤트를 확인했고, 일반 사용자 호출 프로그램의 Authorization Services 반환값을 함께 기록했다.

| 시험             | 관찰 결과                                                                                 |
| ---------------- | ----------------------------------------------------------------------------------------- |
| 서명된 승인      | 권한 status=0, release=0; 호스트 allow=1, helper_exit=0                                   |
| 서명된 거부      | 권한 status=-60005, release=0; 호스트 allow=0, helper_exit=0                              |

처음 의도한 연결 취소는 도구 응답 지연으로 30초 만료에 도달했으므로 만료 증거로 분류했다. 이후 실제 CLI의 요청 수신 이벤트 직후 연결을 끊는 드라이버로 취소를 별도 확인했다. 승인·거부 입력은 에이전트가 수동 승인 CLI를 조작한 시험 입력이며 실제 사람의 생체 인증이나 독립된 PLF02WH 승인 앱 시험이 아니다.

관리자 정리는 `APPROVAL_CLEANUP_OK`, 종료 0이었다. 전용 권한 부재, 보조 프로세스 종료, 기존 screensaver 정의의 원본 일치와 screenUnlockMode 미설정을 확인했다. 로컬 중계·로그 수집을 종료하고 공유 시험물과 새 시험의 비밀키 복사본 6개를 제거했다.

증거는 프로젝트 `private/macos-approval-20261120/trial-c28f8ca2-50e8-4839-a518-87ed414bcd48/`의 `result.json`, `host-events.ndjson`, 각 `*-caller.log`에 있다. 실제 화면 잠금 해제와 키체인 사용 가능 여부는 시험하지 않았다.

- 번들: 프로젝트 `private/macos-approval-20261120/PlfRemoteApproval.bundle`
- 호출 프로그램: 같은 디렉터리의 `run-approval`
- 보조 프로그램: 번들 `Contents/MacOS/approval-helper`
- 서명: 로컬 ad-hoc 서명. Developer ID·공증·제품 배포 서명은 아니다.
- 검증 호스트: 현재 Mac. 다른 macOS 버전의 호환성을 주장하지 않는다.

응답 해시 결합 검사를 제거한 변이본은 `mismatched hash`, 취소 검사를 제거한 변이본은 `reinvoke never allows`에서 실패했다. 변이본은 제거했고 운영 소스는 변이하지 않았다.

실제 Security SDK로 보조 프로그램의 CDHash·hardened runtime·entitlement 부재를 확인했다. 같은 방식으로 서명한 다른 실행 파일인 `run-approval`은 보조 프로그램의 고정 해시 검사에서 거부됐다.

소유자 시험은 신뢰된 보조 프로그램 응답을 제어하는 테스트 어댑터를 사용한다. 자식 수명 시험은 실제 자식을 생성하되 실행·신뢰 경계만 시험용 어댑터로 대체한다. 이 어댑터들은 설치 번들에 포함하지 않는다. 구성요소 시험이 실제 SecurityAgentHelper 호출 성공을 뜻하지는 않는다.

`remote-unlock/`에서 다음 명령으로 재현한다. 보조 프로그램 파이프 시험은 실제 30초 시작 제한을 포함한다.

```sh
bash macos/approval/build-local.sh
bash macos/approval/helper/test-local.sh
bash macos/approval/test-records.sh
bash macos/approval/test-owner.sh
bash macos/approval/test-runner.sh
bun test ./tests --timeout 15000
bun run test:macos
bun run typecheck
bun run lint
bun run format:check
```

시험에서 발견한 오류도 수정했다. 플러그인 전체 수명에 걸쳐 한 번만 실행되던 제한은 한 번에 한 호출로 바로잡았다. 출력 초과 오류 뒤 이벤트 루프가 계속 대기하던 문제는 오류 발생 시 즉시 종료·회수하도록 수정했다.

## 승인받을 변경 범위

첫 설치 시험은 현재 Mac의 로컬 WSS 서버와 전용 시험 키·수동 승인 CLI를 사용한다. 외부 서버 배포나 PLF02WH 승인 앱 시험은 별도 단계다.

1. 프로젝트 내부에서 새 시험 키·CA·서버 인증서와 공개 정책을 준비한다. 정책·공개 CA를 번들에 포함한 뒤 번들을 다시 서명한다. 보조 프로그램의 고정 CDHash는 바꾸지 않는다.
2. Desktop 원본에 대한 과거 관리자 프로세스 접근 제한을 고려해, 승인된 시험물만 `/Users/Shared/` 아래 고유한 임시 디렉터리에 복사한다. 디렉터리는 현재 사용자 소유 0700이며 시험 키는 0600으로 제한한다.
3. 다음 새 항목만 관리자 권한으로 설치한다. 기존 항목이 있으면 덮어쓰지 않고 중단한다.
   - `/Library/Security/SecurityAgentPlugins/PlfRemoteApproval.bundle`
   - `/Library/Application Support/PLF02WHRemoteApproval/requester.private.json`
   - Authorization DB 권한 `org.plf02wh.remoteunlock.approval-test`
4. 번들과 정책·부모 디렉터리는 root 소유로 보호한다. 전용 요청자 키 파일만 현재 사용자 소유 0600이며 부모 디렉터리는 root 소유로 유지한다. 승인자 개인키는 번들·보조 프로그램에 제공하지 않는다.
5. 일반 사용자로 `run-approval approve`와 `run-approval deny`를 실행해 전용 권한의 결과를 확인한다. 취소·시간 초과도 확인한다. 실제 화면 잠금·로그인·FileVault·키체인과 기존 screensaver 규칙은 변경하지 않는다.
6. 시험이 끝나면 설치한 전용 권한·번들·요청자 키를 제거하고 새로 만든 빈 디렉터리와 공유 임시 폴더를 정리한다. 로컬 시험 서버와 승인 CLI도 종료한다.

## 성공 조건과 복구

승인 서명 검증에 성공한 요청만 전용 권한의 성공으로 끝나야 한다. 거부·만료·취소·도중 종료는 허용으로 바뀌면 안 된다. 실제 호스트 호출과 자식 종료·회수 증거를 함께 확인한다. 서명·권한·실행 환경 거부가 발생하면 보호 조건을 낮추거나 다른 경로로 우회하지 않는다.

설치 전에 기존 screensaver 규칙과 관련 설정을 읽기 전용으로 보존한다. 제거는 이번에 새로 만든 항목과 일치하는지 확인한 뒤 수행한다. 기존 파일·다른 프로그램의 인증 규칙은 제거 대상이 아니다. 관리자 인증이 취소되거나 정리가 실패하면 남은 항목을 정확히 보고한다.

보조 프로그램은 사용자 암호나 기존 키체인을 읽지 않는다. 전용 권한에서 Allow가 나와도 실제 Mac 화면 잠금 해제와 잠긴 키체인 사용 가능 여부는 여전히 별도 검증 대상이다.

## 실제 잠금 경로의 후속 진단

2026-11-20 사용자가 기존 잠금 규칙을 보존하는 임시 시험과 원복을 승인했다. 개인용 로컬 프로그램을 목표로 하며 MDM이나 macOS 27 업그레이드를 전제하지 않는다.

후속 진단은 `org.plf02wh.remoteunlock.screen-test` 권한과 항상 거부하는 `PlfAuthProbe:probe`를 사용한다. 서명된 승인을 실제 잠금 해제에 연결한 상태는 아니다. 기존 승인 코드가 사용하는 `isolated-right-test` 계정과 호출자의 UID만으로 실제 잠금 대상 세션을 보증할 수 없어서, 우선 현재 화면 잠금 경로가 진단 메커니즘을 호출하는지 관찰한다.

[원복 도구](../screen-trial/TrialController.swift)는 기존 규칙의 두 항목과 순서를 보존하고 시험 권한만 앞에 추가한다. `screenUnlockMode`는 변경하지 않는다. root 소유 launchd 작업이 5초 주기로 검사하며, 적용 전에 저장한 180초 기한에 도달하면 원래 규칙 구성을 복원한다. 다른 관리자의 정의 변경을 발견하면 덮어쓰지 않는다. Authorization DB가 관리하는 `created`·`modified` 타임스탬프는 구성 비교에서 제외한다.

Swift 6 경고 오류 처리 빌드·서명·plist·쉘 구문 검사와 [규칙·기한 시험](../screen-trial/tests/ScreenRuleTests.swift) 17개가 통과했다. 다른 관리자의 변경도 복원 대상으로 처리하도록 만든 변이는 충돌 보호 시험에서 실패했으며, 소스를 원복한 뒤 정상 빌드와 시험을 완료했다.

실제 설치 환경에서도 임시 규칙 적용과 기한 도달 후 `SCREEN_TRIAL_RESTORED`를 확인했다. 이 이벤트는 원복 도구가 Authorization DB를 다시 읽어 원래 규칙 구성과 같음을 확인한 뒤 출력한다. 이 통합시험 중 사용자에게 화면 잠금을 요청하지 않았다. 실제 화면 해제·대상 세션 결합·키체인 사용 가능 여부는 아직 검증되지 않았다.

### 사용자 조작이 가능할 때까지 중단한 기록

사용자는 현재 Mac 화면을 직접 잠그거나 암호를 입력할 수 없으므로 화면 잠금·인증 시도 없이 다음 단계만 안내해 달라고 요청했다. 이에 대기 중인 관리자 정리 요청을 종료했다. 이전 시험 승인을 근거로 새 인증창이나 잠금 시험을 시작하지 않는다.

중단 후 일반 사용자 권한의 파일 메타데이터 조회에서 아래 경로가 남아 있음을 확인했다. 파일 내용이나 자격 증명은 읽지 않았고 삭제·인증도 수행하지 않았다.

- `/Library/Security/SecurityAgentPlugins/PlfAuthProbe.bundle`
- `/Library/Application Support/PLF02WHRemoteApproval/screen-trial`
- `/Library/LaunchDaemons/org.plf02wh.remoteunlock.screen-trial-restore.plist`
- `/Users/Shared/plf-screen-trial.LQZItx`

당시에는 권한 등록과 launchd 작업의 실행 상태를 추가 조회하지 않았으며 최종 제거가 미완료였다. 원래 잠금 규칙의 자동 복원 성공과 시험 설치물의 최종 제거는 구분해 기록했다.

사용자가 직접 Mac을 조작할 수 있을 때 명시적으로 재개를 요청하면, 남은 설치물의 상태와 정리 범위부터 확인한다. 그 뒤 거부 전용 진단을 다시 준비하고 사용자가 직접 화면을 잠갔다가 평소 방식으로 해제하는 동안 호출 기록을 관찰한다. 호출자·콘솔 관찰값을 인증 대상의 보증으로 간주하지 않으며, 이 진단을 실제 원격 잠금 해제나 키체인 연동의 성공으로 보고하지 않는다.

### 원격 직접 조작 준비 확인 후 정리 완료

사용자가 원격 접속으로 직접 조작할 수 있다고 알린 뒤, 관리자 인증 단계의 내용을 먼저 안내하고 준비 응답을 기다렸다. “준비됐어”라는 응답을 받은 후 정리 명령을 실행했으며 `SCREEN_TRIAL_CLEANUP_OK`, 종료 0을 확인했다. 스크립트는 원래 잠금 규칙 구성을 확인한 뒤 launchd 작업, 시험 권한, 진단 번들과 원복 파일을 제거했다.

공유 임시 폴더도 이번 시험의 파일만 있음을 확인한 뒤 제거했으며 종료 0이었다. 위 중단 기록에 나열한 설치 경로는 이제 정리 완료 상태다. 원복 시험의 공개 설정과 로그는 프로젝트 `private/macos-screen-trial/roundtrip.U17D6u/`에 보존했다.

이 정리 단계에서는 화면 잠금을 시도하지 않았다. 다음 수동 진단에 앞서 원격 접속 방식과 잠금 화면에서 직접 조작할 수 있는지를 확인해야 한다. 이후 인증이나 잠금이 필요한 단계에서도 먼저 안내하고 사용자 준비 확인을 기다린다.

### RustDesk 연결의 읽기 전용 확인
